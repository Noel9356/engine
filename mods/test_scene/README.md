# test_scene — the content mod

The one mod package the engine ships. It owns the demo world end to end: the scene definition (`scene.toml`), the PBR texture sets the scene references (`assets/textures/<set>/`), the Stanford dragon mesh the script imports (`assets/models/dragon.gltf`), the `[renderer].texture_directory` default that points the renderer at the texture sets (`config.toml`), and a script (`script.lua`) that drives the runtime features at startup (spawn, tween, physics body, the dragon import). The engine itself ships no content — deleting this package leaves a working engine that renders whatever the configuration defines (an assembly `[scene]`, or an empty sky), and with no mods at all the engine loads no module.

The package is a script mod because the content needs no native code; the scene is data, not behavior. Its manifest declares `host_capability = "scripting"`, so the kernel hosts the script with whichever active module provides that capability — the package never names a module. The manifest's requirement list is the demand side of the demo run: every capability the demo pipeline consumes (script host, logging, window, input, renderer, lighting, the three radiance layers, screenshot, scene, animation, physics, persistence, ui, asset) is required there, which is exactly why those provider modules load and every other module stays dormant.

The manifest's `scene = "scene.toml"` key is what makes this the *world provider*: the kernel applies the file wholesale when the configuration defines no `[scene]` of its own (precedence and the two-content-mods error are documented in `docs/configuration.md`, "The layer stack").

Texture sets are CC0 from ambientCG (1K): `Bricks070`, `Concrete034`, `Metal049A`, `Plaster001`, `WoodFloor055`. Each is a folder with `Color.png`, `NormalGL.png`, `Roughness.png` and optional `Metalness.png` (Bricks070 and WoodFloor055 also carry an `AmbientOcclusion.png` the renderer does not read); all sets used by one scene must share one resolution (they upload into shared texture arrays), and every set here is 1024x1024.

## The Stanford dragon

`assets/models/dragon.gltf` is a 48k-triangle slice (23k vertices) of the **Stanford dragon** — the vrip reconstruction of the Cyberware 3030 MS scan from *The Stanford 3D Scanning Repository*, Stanford University Computer Graphics Laboratory (http://graphics.stanford.edu/data/3Dscanrep/). The scan is courtesy of the repository's terms: free for research and educational use with this citation. The file is an embedded-buffer glTF 2.0 document (base64 data URI, the importer's documented form) with POSITION accessors only — the importer computes the smooth normals — scaled 8x from the raw 0.14 m scan to a 1.15 m statue, feet at y=0, placed at (0.9, -2.0) beside the metal sphere.

The import runs in `script.lua` at startup: `engine.import_gltf("mods/test_scene/assets/models/dragon.gltf", "mesh")` registers the mesh as `Dragon#n0p0` (deterministic name: node name, node index, primitive index) and spawns the mesh object. The geometry pass rasterizes its actual triangles; the analytic consumers (GI, reflections, shadows) see it through the documented bounding-box proxy.
