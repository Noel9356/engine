# renderer configuration

All keys live in the `[renderer]` section. Default values are in `modules/renderer/config.toml`; `module.toml` `config_keys` documents the section's keys, but the current kernel does not validate module sections against it (only engine sections and plugin manifests are validated). Values are read in `RenderModule::readConfiguration()` (renderer.cpp), re-read on every `ConfigurationReloadedEvent` that touches a `renderer.*` key. Keys are listed alphabetically.

## Keys

| Key | Type | Valid range (as validated in the module) | Default (config.toml) | Effect |
| --- | --- | --- | --- | --- |
| `renderer.anisotropy_level` | float | clamped to 1..16 | `1.0` | Vulkan sampler anisotropy. Clamped again against `limits.maxSamplerAnisotropy` at sampler creation; 1 disables anisotropic filtering. Read on every configuration (re)load; bound into a backend at renderer creation. |
| `renderer.auto_config` | bool | - | `false` | Hardware-derived tuning. When `true`, every performance, quality and memory knob in `[renderer]` is derived from the detected hardware (GPU class and device-local memory via the cached Vulkan probe, logical processor count, installed RAM) and the other tuning keys in `[renderer]` have **no effect**; `clear_color` stays content-owned and is still honored. A one-line stderr notice reports the hardware inputs. Re-derived on every `renderer.*` reload, so toggling the key switches between derived and hand-set values on the next renderer/draw call. See "Auto config" below. |
| `renderer.back_face_culling` | bool | - | `true` | Vulkan pipeline culls back faces; headless uses its winding-probe heuristic. |
| `renderer.backend` | string | `auto`, `vulkan`, `headless` | `"auto"` | Backend selection policy for new renderers. `auto` is hardware-aware: Vulkan when the machine exposes a real GPU (discrete, integrated or virtual device with a graphics queue; software Vulkan implementations report a CPU device class and do not count) and the surface can present to Vulkan, headless otherwise. Errors are reported as-is; there is no silent fallback. |
| `renderer.clear_color` | float[4] | >= 4 components, each finite; clamped to 0..1 | `[0.0, 0.0, 0.0, 1.0]` | Clear color used when `beginFrame` is called with `frame == nullptr`. Content-owned: the one key `auto_config` never overrides. |
| `renderer.device` | string | `auto`, `discrete`, `integrated` | `"auto"` | Vulkan physical-device preference. |
| `renderer.draw_sort_min_commands` | integer | clamped to 2..65536 | `2` | Minimum command count before sorting is worth it. |
| `renderer.draw_sort_mode` | string | `mesh_material`, `material_mesh`, `off` | `"mesh_material"` | `drawMeshes` command sorting; any other value warns and disables sorting. |
| `renderer.frustum_culling` | bool | - | `true` | Sphere-vs-frustum rejection of meshes/instances (both backends). |
| `renderer.gi_indirect_lighting` | bool | - | `true` | Consume the optional `lumen_gi` capability's world-space radiance probe grid and replace the legacy hemispheric ambient with its validity-renormalized SH2 indirect term (full weight once a quarter of the footprint's probes are valid) (see the "lumen_gi probe-grid indirect lighting" section in overview.md). `false` - or the module being absent - keeps the pre-hook hemispheric ambient bit-identical. Read per frame (live-reloadable); the grid version is polled only while enabled. |
| `renderer.reflection_indirect_specular` | bool | - | `true` | Consume the optional `lumen_reflection` capability's screen-space reflection field and add its indirect specular radiance (the expected GGX-lobe response per texel) to the shaded pixels, in linear space before tone mapping (see the "lumen_reflection screen-space field" section in overview.md). `false` - or the module being absent - keeps the pre-hook specular bit-identical. Read per frame (live-reloadable); the field version is polled only while enabled. |
| `renderer.gpu_timestamps_enabled` | bool | - | `false` | Allocate the Vulkan timestamp query pool backing `FrameStatistics::gpuFrameMilliseconds`. |
| `renderer.fur_enabled` | bool | - | `true` | Gate for the shell-fur draw path (`drawFur`/`drawFurInstances`, ABI 13). `false` makes every fur draw a no-op so applications can A/B the fill-rate cost with one config change. |
| `renderer.fur_max_layers` | int | 0..64 | `16` | Hard clamp applied to every fur draw's layer count behind the fur module's LOD policy - the worst-case bound that keeps a buggy policy from turning one fur surface into an unbounded overdraw spike. |
| `renderer.headless_band_split_min_screen_fraction` | number | clamped to 0..1 (warnings outside) | `0.125` | Headless: a draw only pays for a band split when its projected screen extent is at least this fraction of the framebuffer height (small far geometry would spend more on the fork/join than it saves). Read on every configuration (re)load; bound into a backend at renderer creation. |
| `renderer.headless_band_split_triangles` | integer | clamped to 0..1048576 with warnings (0 disables) | `4096` | Headless: draws with at most this many triangles but large screen coverage split the framebuffer by row bands instead of triangle ranges (parallelizes full-screen few-triangle draws such as the floor or sky dome). Read on every configuration (re)load; bound into a backend at renderer creation. |
| `renderer.headless_parallel_transform_vertices` | integer | clamped to 64..1048576 with warnings | `8192` | Headless: meshes at or above this many vertices transform across workers when a task scheduler is available. Read on every configuration (re)load; bound into a backend at renderer creation. |
| `renderer.headless_tile_parallel` | boolean | - | adaptive: `true` with >= 4 logical processors, else `false` | Headless: tile-based parallel rasterization of a single draw (64x64 screen tiles, exclusive per-worker ownership, no per-pixel locks). Triggers mirror the default paths; the serial binning phase makes it slower than the default split on low-core machines (measured ~+55% frame time on 2 cores), so the default follows the logical processor count (the same rule `auto_config` applies). Read on every configuration (re)load; bound into a backend at renderer creation. |
| `renderer.headless_batched_tile_rasterization` | boolean | - | `true` | Headless: rasterize a whole `drawMeshes` command list as one batched tile-parallel pass - every draw's triangles are binned into screen tiles of `renderer.tile_pixels` edge in submission order and each tile is rasterized by exactly one worker, so per-pixel triangle order equals the sequential per-draw replay exactly (equal-depth writes, blended layers and depth-early rejections resolve identically) while the pixel work spreads across every worker. This is the path that lets many-small-draw scenes (streamed LOD chunks, scattered props) use the whole machine: no single draw reaches the per-draw parallel thresholds, but the frame as a whole is large. Requires at least two rasterization workers and takes effect from two workers up (the binning and fork/join run once per frame, not once per draw); oversized frames flush in bounded record chunks that keep submission order. Falls back to the per-draw paths when disabled. Read on every configuration (re)load; bound into a backend at renderer creation. |
| `renderer.headless_transform_cache_mb` | integer | clamped to 0..1024 (MiB) | `256` | Budget for the headless backend's persistent per-mesh transform cache: the world stage is keyed on the model matrix and the draw kind, the clip stage on whichever matrix produced clip, so static geometry under a static camera skips the vertex stage and a camera move reprojects without re-running the model stage. The budget bounds the sum of the cached meshes (least-recently-used entries evict when a new mesh does not fit); 0 disables caching and every draw keeps the direct per-vertex path. |
| `renderer.instance_batch_min_count` | integer | clamped to 2..1024 | `4` | Runs smaller than this fall back to single draws. |
| `renderer.instance_batching` | bool | - | `true` | Fold equal mesh+material runs of `drawMeshes` into instanced draws (Vulkan backend only). |
| `renderer.instance_stream_mb` | integer | clamped to 1..64 (MiB) | `4` | Per-frame instance-matrix ring capacity (also clamped 1..64 at the backend). |
| `renderer.lod_enabled` | bool | - | `true` | Headless mesh LOD chains and angular-size LOD selection. |
| `renderer.lod_min_triangles` | integer | clamped to 0..1048576 with warnings | `4096` | Headless: meshes below this triangle count get no LOD chain. Read on every configuration (re)load; bound into a backend at renderer creation. |
| `renderer.lod_strides` | array of numbers | three strictly ascending values in 2..1024 (warnings keep the current strides) | `[4, 16, 64]` | Headless: the triangle strides of the decimated LOD chains above the base level; level 0 is always the full index list. Read on every configuration (re)load; bound into a backend at renderer creation. |
| `renderer.lod_thresholds` | array of numbers | four finite strictly descending values in (0, 1] (warnings keep the current cutoffs) | `[0.02, 0.05, 0.1, 0.2]` | Headless: angular-size cutoffs (scaled bounding radius / distance) at which `drawMesh` picks a coarser LOD chain. Read on every configuration (re)load; bound into a backend at renderer creation. |
| `renderer.max_frames_in_flight` | integer | clamped to 1..8 | `3` | Number of Vulkan frame slots (command buffers + fences). |
| `renderer.max_material_sets_per_renderer` | integer | clamped to 1..65536 | `256` | Vulkan: maximum number of cached material descriptor sets per renderer. The Vulkan descriptor pool is sized from this limit. |
| `renderer.max_pending_uploads` | integer | clamped to 1..4096 | `64` | Cap on in-flight staging upload submissions; the oldest is waited on when full. |
| `renderer.max_textures_per_renderer` | integer | clamped to 1..65536 | `256` | Vulkan: maximum number of textures held by each renderer. Rejection occurs when the cap is reached; textures are not evicted automatically. |
| `renderer.memory_budget_update_interval_frames` | integer | clamped to 0..3600 | `120` | Frames between VMA device-local budget/usage refreshes (0 disables). |
| `renderer.msaa_samples` | integer | clamped to 1..8 | `4` | Anti-aliasing sample request, honored by both backends. Vulkan: values > 1 select the dynamic-rendering path with a multisample color attachment (`DONT_CARE` store + `RESOLVE_MODE_AVERAGE` resolve); requires dynamic rendering support and color/depth formats that support the sample count, otherwise the renderer falls back to 1 sample with a one-time note. Headless: the request maps to the smallest integer supersampling grid of {1x1, 2x1, 2x2, 4x2} holding at least the count (1 -> 1, 2 -> 2x1, 3/4 -> 2x2, 5..8 -> 4x2 samples per pixel); the rasterizer shades that many pixels per output pixel and presentation averages each block (the software counterpart of the Vulkan resolve). Read on every configuration (re)load; bound into a backend at renderer creation. |
| `renderer.parallel_triangle_threshold` | integer | clamped to 1..1048576 with warnings | `4096` | Headless: triangles per draw before splitting across task-scheduler workers. Read on every configuration (re)load; bound into a backend at renderer creation. |
| `renderer.pipeline_cache_mb` | integer | clamped to 0..512 MiB | `64` | Vulkan: maximum persistent pipeline-cache data loaded from or saved to disk. `0` disables disk persistence while keeping the in-memory Vulkan cache active. |
| `renderer.pixels_per_lock_group` | integer | clamped to 1..4096 with warnings | `16` | Headless: pixels per depth lock group during parallel rasterization. Read on every configuration (re)load; bound into a backend at renderer creation. |
| `renderer.present_mode` | string | `auto`, `fifo`, `mailbox`, `immediate` | `"auto"` | Vulkan swapchain presentation-queue policy. `auto` keeps the historical vsync-derived choice (FIFO when vsync, else mailbox-fallback-immediate); `fifo` is always tear-free but blocks the present on the compositor; `mailbox` triple-buffers for the lowest-latency tear-free path; `immediate` never waits on the display (lowest latency, may tear). Read on every configuration (re)load; bound into a backend at renderer creation. |
| `renderer.srgb_output` | bool | - | `false` | Selects the sRGB output target: the Vulkan swapchain prefers an `_SRGB` surface format and the shader's `SRGB_OUTPUT` specialization constant follows it; the headless target always writes UNORM with its fixed encode. Read on every configuration (re)load; bound into a backend at renderer creation. |
| `renderer.texture_mipmaps` | bool | - | `true` | Generate full mip chains for textures (Vulkan: requires RGBA8 blit support, otherwise disabled with a warning; the headless sampler always reads the base image). |
| `renderer.tile_pixels` | integer | clamped to a power of two in 16..256 with warnings | `64` | Headless: the screen-tile edge of the tile-parallel rasterization paths (per-draw and batched); the tile grid aligns with the framebuffer at power-of-two edges. Read on every configuration (re)load; bound into a backend at renderer creation. |
| `renderer.validation` | bool | - | `false` | Enable VK_LAYER_KHRONOS_validation + debug utils (only when the layer is installed; warns otherwise). |
| `renderer.vsync` | bool | - | `false` | Vulkan present mode: FIFO when on; mailbox (fallback immediate) when off. Off is the default for the lowest P99 frame time - Mailbox triple-buffers and never blocks the CPU on the compositor/vblank. |

`renderer.srgb_output` (boolean, default `false`) selects the sRGB output target: the swapchain prefers an `_SRGB` surface format and the shader's `SRGB_OUTPUT` specialization constant follows it; the headless target always writes UNORM with its fixed encode (see backends.md). The active resource and persistent pipeline-cache limits are configurable through the keys documented above.

## Auto config

`renderer.auto_config = true` replaces the whole `[renderer]` overlay with a hardware-derived set (`applyHardwareDerivedConfiguration` in renderer.cpp). The derivation inputs are the cached GPU probe (`probeHostGpu` in vulkan_gpu_probe.cpp: device class, device-local heap bytes, sampler-anisotropy and timestamp feature bits), the logical processor count and the installed physical RAM (`engine/util/hardware_info.hpp`); unknown inputs fall back to the conservative end of each range. Derived values (all within the validated ranges above):

- `backend`: Vulkan when a real GPU is present, headless otherwise (identical to the `backend = "auto"` policy). `device`: `discrete`/`integrated` when the probe unambiguously found that class, `auto` otherwise.
- `vsync` on, `validation` off, `max_frames_in_flight` 2.
- `max_pending_uploads` 64 (16 when RAM is under 4 GiB or unknown); `headless_transform_cache_mb` 256 on >= 8 GiB machines, 128 below, 64 under 4 GiB.
- `max_textures_per_renderer` / `max_material_sets_per_renderer` 512 only for a discrete GPU with >= 6 GiB of device-local memory, else 256; `pipeline_cache_mb` 128 (discrete), 64 (other GPU), 32 (headless); `instance_stream_mb` 8 for big-VRAM discrete GPUs, else 4.
- `msaa_samples` 4 for a discrete GPU with >= 6 GiB, else 2 (anti-aliasing stays on in every derived tier; only the sample count scales); `anisotropy_level` 8 (discrete) / 4 (integrated, virtual) when the device supports sampler anisotropy, else 1.
- `gpu_timestamps_enabled` only when a GPU exposes timestamp-capable queues.
- Sorting (`mesh_material`), instance batching (min 4), mipmaps, frustum/back-face culling and LOD on.
- Headless threading scales with the CPU: the per-draw tile path from 4 logical processors, the batched tile path (whole draw lists) from 2, parallel triangle thresholds 2048 on >= 8 processors (else 4096).

The manual ranges still apply as the outer bounds; auto_config never sets a value the hand-written path would have clamped.

## Hardware probing notes

The probe runs once per process on first use (a bare `VkInstance` without extensions, `vkEnumeratePhysicalDevices`, static properties only - no logical device, no surface). It is also what makes `backend = "auto"` hardware-aware. On a machine whose only Vulkan implementation is a CPU rasterizer (lavapipe, SwiftShader) the probe reports `gpuPresent == false`, so both `auto` and `auto_config` choose the engine's own headless CPU backend instead of routing frames through a software Vulkan driver. When the build has no Vulkan backend at all, the probe reports no GPU and every auto path deterministically picks headless.

## Out-of-range and malformed values

Behavior as implemented in `readConfiguration()` (renderer.cpp):

- Integer keys with a validated range are clamped into the range and a warning is printed to stderr, e.g. `renderer module: clamping [renderer] max_frames_in_flight 99 to range 1..8`. The clamped value is used.
- `clear_color` requires at least four components; a shorter array is silently ignored (no warning). If any component is non-finite the whole array is ignored with a warning; otherwise each component is clamped to 0..1.
- String enums (`backend`, `device`, `draw_sort_mode`) warn on unknown values and fall back (`auto` for backend/device, sorting disabled for draw_sort_mode). Unknown `draw_sort_mode` values never enable sorting.
- The headless tuning keys are validated in `readConfiguration()` on every (re)load: out-of-range values are clamped with a warning (the ranges are documented per key above), so a hardware-derived renderer is indistinguishable from a hand-tuned one. The headless threading keys (`parallel_triangle_threshold`, `headless_band_split_triangles`, `headless_parallel_transform_vertices`, `pixels_per_lock_group`, `headless_tile_parallel`, `headless_batched_tile_rasterization`, `lod_min_triangles`) only take effect when a renderer is created. `headless_tile_parallel` is the one headless key without an entry in config.toml: its adaptive default (four logical processors and up) is the shipped value, and an explicit line would pin it for every host.
- Every key in `config_keys` has a reader in the module; settings outside the keys above still do nothing (module sections are not known-key validated). The hard-coded values listed in the removed-keys note are the effective behavior for areas the module does not parameterize yet.

Note that the module's built-in defaults before configuration is applied deliberately differ from config.toml for opt-in features (sorting, batching, mipmaps start disabled in code); with the shipped config.toml the table above is what actually ends up active. `module.toml` `config_keys` documents the section's surface; settings outside these keys are not validated by the kernel (it validates only engine sections and plugin manifests).

Keys that affect a renderer's immutable objects (`backend`, `device`, `msaa_samples`, `anisotropy_level`, and the headless threading keys) are read on every configuration (re)load and bound into a backend when `createRenderer` runs; a reload changes what the *next* `createRenderer` sees, never a live renderer. See [overview.md](overview.md) for the lifecycle and [backends.md](backends.md) for the per-backend behavior.
